Blanc/Deployed bytecode/EIP-7002 contract

The EIP-7002 contract.

Since Prague, every validator exit or partial withdrawal triggered from the execution layer passes through these 504 bytes, written by hand in assembly. At the end of every block the client calls the contract, and a block whose call fails is invalid.

With its canonical code installed, Blanc proves that this end-of-block call succeeds whatever the contract’s storage holds; that each block’s requests are exactly the oldest pending submissions, in order, none dropped, duplicated, reordered or emitted early; and that the EIP’s own fee guarantee is false of these bytes — while showing exactly where, and how far beyond any account’s reach, the deployed arithmetic departs from the specification. Mainnet met the theorems’ starting premises when Prague began.

The protocol’s own code

What the contract does.

A user submits a 56-byte request — a validator’s public key and an amount — with a fee, and the contract queues it, with the caller, at raw storage offsets. At the end of every block the client calls the contract from the reserved system address 0xffff…fffe; the contract removes up to sixteen requests from the head of the queue, returns them as the block’s withdrawal requests, which the block header commits to, and updates an excess counter that sets the next fee through fake_exponential(1, excess, 17). A fault here could drop, duplicate or reorder exits, or invalidate blocks.

With no compiler, no ABI and no selector dispatch, the contract also tests whether the method depends on a compiler’s conventions. It needed no extension of the certificate checker. The model the bytes are proved to refine is transcribed from the EIP’s text and pseudocode, not read off the bytes. Its initial state is what deployment leaves: the excess set to an inhibitor, 2256 − 1, that blocks submissions until the first system call, and an empty queue.

Totality

A system call that cannot fail.

Whatever the contract’s storage holds, as long as its canonical code is installed, the client’s end-of-block call succeeds without error, at an exact, state-dependent cost that never exceeds 210,000 gas — against the 30,000,000 the protocol supplies. The statement has two hypotheses: a covered fork, and the code.

Statement, verbatimBlanc.Lift.WithdrawalRequest.checked_system_totality · SystemProtocol.lean:245
theorem checked_system_totality {benv : Benv} (fork : CoveredFork benv.stat.fork)
    (installed : benv.state.getCode withdrawalRequestPredeployAddress = Blanc.withdrawalRequestCode) :
    processCheckedSystemTransaction benv withdrawalRequestPredeployAddress [] =
      .ok ((systemProtocolPost benv).state, systemProtocolOutput benv) ∧
    (systemProtocolOutput benv).error = none ∧
    (systemProtocolOutput benv).gasLeft = systemTransactionGas - systemProtocolGas benv ∧
    systemProtocolGas benv ≤ 210000 ∧
    (systemProtocolOutput benv).returnData = (systemProtocolPost benv).output ∧
    (systemProtocolOutput benv).refundCounter = (systemProtocolPost benv).refundCounter

Its history form, history_checked_system_totality, needs only that the canonical code is installed at a checkpoint: after any configured history from there, the call still succeeds. No history removes the code, and nothing a history does to this contract’s storage can make its end-of-block call fail and the block invalid — in Jaune’s semantics.

Safety, after any history

Submissions in, requests out.

From a checkpoint whose storage represents the initial state, for every block of a configured history, the requests the block hands to the consensus layer are exactly the first queued entries, at most sixteen, in first-in-first-out order, and each is the caller, public key and amount of exactly one committed submission, which paid the fee the bytecode computed. No committed submission is dropped, duplicated, reordered or emitted before it was made; the entries not yet emitted are exactly the queue that storage holds afterwards; and the queue never reaches the four bookkeeping slots.

The premises are trace-local and finite. The contract recognizes the system call only by its caller, so the history must contain no transaction from the system address, no EIP-7702 authorization signed by it and no creation addressed to it, even a failed one, and the address must hold no code at the checkpoint; the four system contracts must hold their canonical code there; and the history may contain at most 2254 committed submissions. There is no hash premise, and no entry condition on the frames that run the contract.

A companion bounds delivery. An entry at position q of the queue when a block’s requests are computed is emitted exactly ⌊q/16⌋ blocks later, counting that block as zero, in every configured extension of the history that long — and nothing submitted later overtakes it (block_word_delivery). Beneath both lies an exact replay: the storage at the end of any such history represents the EIP’s model replayed over exactly the committed submissions and system calls, in order (history_word_storage_replay).

Statements that can fail

The system-address premise is not decorative.

A closed theorem builds a two-block configured history that meets every other premise of the request theorem but places, at the system address, a contract that calls the queue from inside a user transaction and drains it before the block’s own system call — and the conclusion fails (systemEmpty_loadBearing_witness). As far as we know, putting code at that address would take a signature by its key or a 160-bit Keccak preimage, but Blanc does not prove this, and the premise stays.

Refinement and liveness

Every successful frame, classified.

A successful frame at this code is exactly one of three things, with exact storage, logs and return bytes: the system call’s dequeue; a submission — not static, from a caller other than the system address, with 56 bytes of input and a value covering the fee the bytecode computes; or a fee read. While the excess holds the inhibitor, no user call succeeds. Which failure a rejected call meets is not stated (exec_frame_effect). The contract’s balance never decreases, and the committed submissions add exactly their values to it (history_balance_nondecreasing).

After any history that leaves the contract active, a submission paying at least the EIP’s fee and started with more than the 2,300-gas stipend beyond its cost executes at exactly 1,258 + 87·k gas plus its storage accesses, where k counts the iterations of the fee loop; a fee read costs 180 + 87·k plus one read (history_submission_nat_live).

Specification against bytes

The fee the bytes compute.

The EIP specifies its fee as Python pseudocode over unbounded integers. The bytecode computes the same series in 256-bit words, whose intermediate products can overflow. Two pre-deployment audits noted that its fee therefore departs from the EIP’s once the excess passes 2,892: one judged such an excess unreachable under current settings; the other, noting that a higher block gas limit might bring it within reach, rated the finding informational. Blanc states the agreement exactly.

The bytecode’s fee never exceeds the EIP’s, and equals it exactly when no intermediate value of the series wraps. Then a closed theorem builds a three-block configured history, under the premises of the request theorem, in which a submission is committed after paying 2245 wei: at least the fee the bytecode computes at an excess of 2,893, about 3.2·1073 wei, but less than the EIP’s, about 8.1·1073 wei (nat_fee_guarantee_refuted). The guarantee that every committed submission paid at least the EIP’s fee is therefore false of the deployed bytes — which is why the request theorem speaks of the fee the bytecode computes.

The divergence begins only where the EIP’s own fee is out of any account’s reach. By direct computation, outside the proofs, the two fees agree at every excess below 2,893, and at 2,892 the fee is already about 7.6·1073 wei, more than 1047 times all the ether in existence. The wrapped arithmetic does yield a fee of 1 wei near an excess of 2252, but every model state a history reaches from deployment has its effective excess plus its count bounded by the number of submissions, so that excess would take about 2252 of them. The counterexample reaches its excess with 2,895 submissions in one block, on a synthetic Prague chain whose block gas limit, 229, is about nine times mainnet’s; on mainnet the excess has so far peaked at 666, on 19 December 2025.

The seventh question

Mainnet, when Prague began.

The contract was deployed before Prague, but its use began only when Prague activated, so all of it lies in forks Jaune covers. At block 22,431,083, the last before Prague, three providers report that its storage held exactly the model’s initial state — the inhibitor in the excess slot, zeros in the count, head and tail — with the same storage root it had at deployment, 549,694 blocks earlier; that it had logged no request; that the four system contracts held their canonical code; and that the system address held none.

Mainnet’s state when Prague activated, as the providers report it, therefore met the checkpoint premises of the request theorems. What separates those theorems from the live contract is the premise that mainnet’s history is a configured one, which rests on Jaune’s fidelity, and the exclusions at the system address. Under every covered fork, executing the recorded keyless creation input installs the certified runtime and leaves storage representing that initial state, with no hash premise (deploy_initial).

Stated, so it is not inferred

Not claimed.

  • How the consensus layer processes the requests, including whether the caller is entitled to act on the validator it names.
  • Whether the fee parameters are economically sound.
  • That the chain produces the later blocks the delivery bound speaks of; distance is counted in configured blocks.
  • Which failure a rejected call meets, or its gas.
  • Storage growth: dequeued slots are left in storage, and nothing is proved about them.
  • Transaction-level liveness; anything beyond 2254 committed submissions.

The claim map’s EIP-7002 section lists every theorem with its premises, file and line.

Context

Earlier work.

Before deployment, four audits commissioned by the Ethereum Foundation examined the Pectra system contracts, and a loop-bounded Halmos check compared this contract’s bytecode with references written from the EIP’s pseudocode. We know of no earlier proof about this contract that is unbounded in the excess and in the history, or that follows a request from its submission to the block that emits it.
