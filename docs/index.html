EVM bytecode, verified in Lean 4

Nothing but
the bytes.

Blanc proves theorems about Ethereum contracts as they are deployed: the exact bytes at mainnet addresses — compiled by solc and Vyper between 2017 and 2026, or written by hand in assembly — read without trusting the tools that produced them.

Every theorem is stated against Jaune, an executable semantics of the EVM and of block processing that passes all 34,205 blockchain-test cases of Ethereum’s tests@v20.0.2 fixtures for the forks in force since May 2025. Lean’s kernel checks every proof, and none uses an axiom beyond Lean’s three standard ones. Gas is exact, so a theorem can say not only that a contract keeps its books, but that a transaction sent to it is admitted, and exactly what it costs.

What a result should answer

Six questions to ask of any verification result.

Each has been answered before; to our knowledge, never all six at once. For the eight artifacts above, Blanc answers every one.

Is it about the code that runs?

About the deployed bytes themselves, not the source and not a recompilation, so no compiler stands in the trust base. In 2023 that distinction cost Curve’s pools: their source asked for one shared reentrancy lock, and the compiler emitted one lock per function.

What does the proof rest on?

Lean’s kernel and its three standard axioms, propext, Classical.choice and Quot.sound. A walk from all 102,646 constants of the library reaches nothing else: no sorry, no native evaluation, no axiom about Keccak-256.

Was the code written for the verifier?

No. Seven compiler versions and an assembler, from unoptimized solc 0.4.19 output of 2017 to 504 bytes of hand-written assembly the protocol runs. None of it was shaped for Blanc’s tools.

Is the machine the real machine?

Jaune defines the machine, every transaction type, block validation, system calls, withdrawals and requests, every precompile from ecrecover to BLS12-381, and fork selection by schedule — and it runs: 34,205 of 34,205 blockchain-test cases pass, run through the core of the block transition the theorems quantify over. Its gas schedule meets the chain too: in a 30,000-block window, every WETH9 withdraw of the proved shape whose starting balance the logs determine — 3,748 of 3,780 — used exactly the gas Blanc proves, and so did all 542 Uniswap-pair approve calls compared, counting the standard intrinsic charge on top of the proved frame cost.

Does the theorem matter?

The properties are the ones people rely on: balances that stay backed, deposits accumulated exactly, withdrawal requests delivered first in, first out, a lock that actually excludes, a ledger that balances.

Does it say the contract works?

A contract that always reverts satisfies every invariant. Exact gas lets Blanc construct successful executions too: WETH9’s withdrawal is admitted as a signed transaction after any history; the Uniswap pair’s state-changing functions run at closed costs; the EIP-7002 system call succeeds whatever storage holds.

And a seventh: does a theorem’s starting point hold of the live contract?

For the EIP-7002 contract, yes: at the last block before Prague, mainnet’s storage held exactly the model’s initial state, with the storage root it had at deployment. The CircuitBreaker’s live registry, read from three providers, passes the finite tier’s decidable check on 29 probes, evaluated by a script rather than by the kernel. WETH9, the deposit contract, 3Crv and the Uniswap pairs predate the forks Blanc covers; their theorems start from a modeled fresh deployment, and checking their invariants against complete live storage is the next step.

Selected results

What the theorems say.

The protocol’s own code

A system call that cannot fail, and a queue that cannot cheat.

EIP-7002 contract · 0x0000…7002 · 504 bytes · hand-written assembly

Since Prague, every withdrawal request triggered from the execution layer passes through a 504-byte contract, and a block whose end-of-block call to that contract fails is invalid. With its canonical code installed, Blanc proves that this call succeeds whatever the contract’s storage holds, using at most 210,000 gas, and that no history removes the code. Each block’s requests are exactly the oldest pending submissions — at most sixteen, in order, none dropped, duplicated, reordered or emitted early — and an entry at position q of the queue is emitted exactly ⌊q/16⌋ blocks later.

The same bytes refute the EIP’s own fee guarantee. The specification computes its fee over unbounded integers; the bytecode computes it in 256-bit words. Blanc proves the bytecode’s fee never exceeds the specified one, equals it exactly when no intermediate value wraps, and builds a three-block history in which a committed submission paid less than the EIP requires. By direct computation the two fees first differ where the specified one already exceeds all the ether in existence more than 1047 times; two pre-deployment audits had flagged the overflow.

Curve StableSwap pools

The bug that compiled, and the fix.

Vyper 0.2.15 · 0x6326…B43E · and Vyper 0.3.7 · 0x847e…4ed9

On 30 July 2023, attackers drained several Curve pools. Their source marked every liquidity function @nonreentrant('lock'), asking for one shared lock; Vyper 0.2.15, 0.2.16 and 0.3.0 gave each function a lock of its own. A proof about the source would have certified the guard.

Blanc reads the bytes. On the vulnerable implementation behind three of the drained pools, Jaune executes the attack from deployment: remove_liquidity takes its lock in slot 2 and sends ether; the callback enters add_liquidity, whose lock sits in slot 0, and mints; the outer call writes back a stale supply. The ledger ends at a supply of 1,800 against an attacker balance of 1,906. On an implementation compiled by Vyper 0.3.7, Blanc proves that while any of its five mutating guarded functions holds the lock, no frame beneath it enters any of the seven guarded functions — whatever code runs in between, given only that no hash the pool computes lands on the lock’s slot.

Uniswap V2

One runtime, every pair.

solc 0.5.16 · 11,293 bytes · 524,109 pairs

Uniswap V2’s factory deploys every pair from one creation code, so a single 11,293-byte runtime runs at all 524,109 of them, and Blanc’s theorems quantify over the pair, its tokens and its factory. After any valid history, from a state representing the Solidity model, the pair’s storage represents that model replayed over exactly the committed calls, with calls made back into the pair through a token or the flash-swap callback replayed inside the step that made them. The LP ledger stays balanced; the price accumulators obey their law, wrap-around included; and, under a premise on the tokens’ actual answers, the geometric mean of the reserves per LP token falls only through the protocol fee.

A pair learns its balances only from what tokens answer. Those answers are inputs of the statements, never assumptions folded into definitions: the replay, ledger and oracle theorems take no premise about any token or the factory. All ten state-changing functions run at closed gas costs whenever the model accepts the call, given, for the six that call out, their callees’ replies.

The Beacon deposit contract

Exactly the deposits made.

0x0000…05Fa · 6,358 bytes · solc 0.6.11

Every validator deposit on Ethereum mainnet has passed through this contract, which holds about 91.8 million ether and has counted 2,565,727 deposits. It keeps an incremental Merkle tree of depth 32 over the deposit data. After any valid history from a state that accumulates some list of deposits, Blanc proves its storage accumulates that list followed by exactly the committed deposits, in order; the count slot holds their number, and the root is their reference Merkle root — the incremental algorithm is proved to compute it for every hash function, and the history theorems instantiate the hash as Jaune’s SHA-256. A deposit the model accepts executes at exact gas and extends the tree by exactly its own node. No hash premise appears anywhere.

How it works

Read the bytes, check the reading, prove about the reading.

EVM bytecode has no structured control flow, and recovering it is a heuristic art. Blanc does not trust whoever performs it. An untrusted program proposes a certificate, a structured reading of the bytes; a decision procedure evaluated by Lean’s kernel accepts it or rejects it against the literal bytes; and generic theorems, proved once for every certificate, carry reasoning about the reading back to the bytes.

  1. Runtime bytesexactly as deployed
  2. Produceruntrusted; proposes entries, abstract stacks and trees
  3. Kernel checkCert.check, Cert.jumpsOk against the literal bytes
  4. Generic theoremslift_sound, lift_exact, the cursor
  1. Frameone execution of the code
  2. Messagechild calls, reverts, settlement
  3. TransactionprocessTransaction: validity, intrinsic gas, refunds, fees
  4. Historyany valid chain of blocks from a checkpoint

lift_sound

Every successful execution of the bytes from program counter 0, on a covered fork, is a run of the certificate’s program — so safety properties of the program hold of the bytes.

lift_exact

Every gas-exact run of the program is a successful execution of the bytes — so a run built forward, one node at a time, becomes a real execution with its exact cost.

The cursor

Places every step of an execution, whatever its outcome, at a checked node of the certificate. A reentrancy lock needs this: a frame that later reverts has still run.

What you trust

A small kernel, three axioms, and two facts the proofs take from the world.

1,105leaf results — theorems nothing else builds on — all covered by one axiom walk

34,205conformance cases Jaune passes, of 34,205 selected, at the revision Blanc pins
86gates in the catalogue, all executed afresh and passing at commit 5048a51f

Checked by the kernelEverything that is proved

  • Every proof, including every certificate check against the literal bytes it reads.
  • The axioms: one from-scratch walk over every declaration of the library reaches propext, Classical.choice and Quot.sound and nothing else. It does not rely on #print axioms, which can under-report.
  • The statements: an example per pin restates each headline theorem, and each definition its claim is stated through, exactly.
  • The public account: a gate resolves every declaration the claim map cites to its file and line and recomputes every artifact’s code hash from the lifted bytes.

Trusted, and testedWhat the proofs do not establish

  • That Jaune’s definitions match Ethereum. Not provable; tested by the fixtures above, run through the core of the block transition the theorems quantify over.
  • That the lifted bytes are the chain’s. Three separately operated providers return identical code for every address; this is recorded provenance, not yet a proof from a block’s state root.

And every theorem has premises. Whoever applies one must discharge its hypotheses, and its statement is its specification: the kernel checks proofs, not whether a statement says what a reader wants. The statements are written to be read, and the claim map locates every one.

Blanc, the language

For bytes not yet written: a language whose compiler is a theorem.

Blanc began as a programming language: the EVM’s own instructions, arranged by four constructors. Its compiler’s correctness is a Lean theorem, so a property proved of a Blanc program is a fact about the bytes that deploy. Ten contracts are written in it and verified over their compiled bytes, and the history, settlement and liveness machinery they needed is what the lift of deployed bytecode now stands on.

Writing in Blanc buys what reading cannot: storage laid out so that a wrapper’s solvency needs no hash premise at all; runtimes smaller than their references in six ports of seven — WETH in 988 bytes against WETH9’s 3,124; and every implementation choice open, down to the instruction.

Who wrote the proofs

Written by agents. Checked by the kernel.

The lift of deployed bytecode — 236,372 lines of Lean in 912 files — was written by AI agents in fifteen days, from 25 September to 9 October 2026, under one author’s direction and on top of the existing stack. The coordinator–worker workflow they ran in, Creme, accepts a result only on the gate catalogue’s verdict for the exact commit.

Lean’s kernel checks an agent’s proof exactly as it checks a person’s. The trust never lived in the author; it lives in the kernel, the axioms, and the statements, which are there to be read.

Limits

Where the theorems stop.

Each artifact’s page and the claim map state these precisely; here they are in one place.

Every disclosure, item by item

  1. Live state. The deployment theorems run each recorded creation input under current rules; they do not prove the historical transaction was included. Applying the history theorems to today’s WETH9, deposit contract, 3Crv and Uniswap pairs needs their invariants checked on complete live storage, a finite computation over public data not yet done.
  2. Amsterdam. Jaune runs it, but no theorem here is stated for it: every history theorem requires each block to run under Prague, Osaka, BPO1 or BPO2.
  3. Premises. Signature recovery, for theorems over every signed transaction; callee behaviour, where success depends on another contract; hash separation over the keys a history touches, and for the CircuitBreaker’s history tier over all addresses; for EIP-7002, at most 2254 committed submissions.
  4. Byte identity. That the lifted bytes are mainnet’s rests on providers agreeing, not on a proof from a block header’s state root.
  5. One contract at a time. The Uniswap theorems take the tokens’ answers as inputs; no theorem yet composes the pair with WETH9 or with its factory.
  6. Messages, not transactions. The Vyper executions from deployment are sequences of messages, with synthetic token, attacker and receiver code.
  7. Admission, not inclusion. Liveness theorems execute a transaction at a given state or block position and say exactly what it does and costs; whether any block will include it is outside them.
  8. Constant jump targets. Certificates accept a jump only to a known constant destination or a function’s own return address; code that jumps to computed targets cannot yet be certified.

Check it yourself

One clone, one build, and the gates.

You need git, curl, Python 3 and elan, Lean’s toolchain manager. Blanc pins Jaune by an immutable commit in its lakefile, so “which semantics was this proved against” always has a one-line answer.

The axiom walk follows every constant of the library once and reports the leaf results; the pin gate elaborates every pinned statement; the claim-map gate checks the public account of the deployed results against the tree; the certificate gate regenerates every certificate from its input and compares it byte for byte. scripts/check-gates.sh --fresh runs the whole catalogue, whose commands and pass criteria are in scripts/GATES.md.

$ git clone https://github.com/skbaek/blanc && cd blanc$ lake exe cache get$ scripts/check.shOK — axiom audit: one union walk over Blanc reaches only the standard axioms; 1105 leaf results$ scripts/check-claims.shOK — claim statements: 758 definitions/statements and exact record constructors pinned by Lean$ scripts/check-deployed-claim-map.sh$ scripts/check-lift-certificates.sh

scripts/check.sh builds the library before it walks the axioms. The two verdict lines illustrate successful runs at the generated counts; run the commands to obtain a verdict for your checkout. Rebuilding the 1,482 modules the library’s root imports, from source, with the toolchain and pinned dependencies already built, took 4,380 seconds on a 10-core Apple M5 with 24 GiB of memory.
