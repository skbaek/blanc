# Blanc WETH deviations from deployed WETH9

Blanc's WETH is a proof-oriented reimplementation, not a source or bytecode
model of the WETH9 contract deployed at
[`0xC02a…6Cc2`](https://etherscan.io/address/0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2#code).
This registry catalogues observable semantic differences found by comparing
`Blanc/Weth.lean` with the canonical
[`WETH9.sol`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol).

Each row cites Blanc's side by **declaration name and module** rather than by
line number. The citations were originally line ranges into `Blanc/Weth.lean`;
by 2026-08-05 all ten had drifted, three of them past the end of a 237-line
file, and three named `Blanc/Weth.lean` for `transfer`, `balanceOf` and
`allowance`, which live in `Blanc/CommonCore.lean`. They were re-derived by
reading, in the same repair `FMINT_DEVIATIONS.md` records for its own
coordinates. Names do not rot; line numbers do.

The first four rows are the four **claims** the fixture suite and
`gen-weth-fixtures.py` refer to by number; they are in a fixed order and new
rows go at the end. The fourth and fifth rows are no longer deviations — each
is an **agreement** that used to be one, kept in the table rather than under
*Checked similarities* because its history is what several of this suite's
harness accommodations were about: row 5 became an agreement with the
2026-08-05 `Func.rev` normalization, and row 4 with the 2026-08-09
`nonpayable` conformance change.

| Behavior | Deployed WETH9 semantics | Blanc semantics | Observable consequence | Project stance | Fixture evidence |
|---|---|---|---|---|---|
| Address words with nonzero upper 96 bits | Solidity's address parameters are 160-bit values. The deployed Solidity 0.4.x decoder ignores dirty higher-order bits, so calls resolve the low 160-bit address ([Solidity compatibility note](https://docs.soliditylang.org/en/v0.7.6/050-breaking-changes.html#semantic-only-changes)). | Mutating paths reject such words, each through `checkNonAddress` (`approve` and `transferFrom`, `Blanc/Weth.lean`; `transfer` via `transferTestDst`, `Blanc/CommonCore.lean`). The `balanceOf` and `allowance` views instead use the full calldata words as storage-key material without an address check (`balanceOf` and `allowance`, `Blanc/CommonCore.lean`). | A noncanonical ABI word that WETH9 aliases to its low-160-bit address either reverts in a Blanc mutator or queries a different Blanc storage key. | No equivalence claim; callers should use canonical ABI encoding. | Discharged by [`10-deviation-address.json`](scripts/fixtures/weth/10-deviation-address.json): the mutators refuse the dirty word in every position while honouring the canonical alias, and `balanceOf` answers different values for the two — neither masking nor checking. |
| Balance storage layout | `balanceOf` is a Solidity mapping declared first ([`WETH9.sol:28`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L28)), so balances occupy mapping-derived slots rather than slots equal to addresses. | Deposits and transfers use the raw 256-bit address word itself as the storage slot (`deposit`, `Blanc/Weth.lean`; `transfer`, `Blanc/CommonCore.lean`). | Blanc storage proofs and states cannot be interpreted as WETH9's deployed storage image; the same account's balance lives at a different slot. | Deliberately simple proof-oriented representation; no storage-layout compatibility claim. | No case of its own — structural, and witnessed by every case in the [fixture suite](scripts/fixtures/weth/README.md#known-limits-of-these-expectations), each of which asserts storage at exactly the raw-address-word keys. |
| Allowance storage layout and collision handling | `allowance` is a separate nested Solidity mapping ([`WETH9.sol:29`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L29)); Solidity's [mapping layout](https://docs.soliditylang.org/en/latest/internals/layout_in_storage.html#mappings-and-dynamic-arrays) domain-separates it from `balanceOf` through the declared base slots. WETH9 has no fail-on-hash-collision branch. | Blanc stores an allowance at `keccak256(src ‖ dst)`. If that 256-bit hash is also a valid raw-address balance key, `approve` and allowance-consuming `transferFrom` revert instead of writing or reading through the collision (`prepApprove`'s `checkAddress` and the guard `approve` forks on, and `updateAllowance`'s `checkAddress` on the `transferFrom` path — all `Blanc/Weth.lean`). | The allowance key is incompatible with WETH9 storage. In the exceptional collision case, an operation WETH9 permits fails in Blanc; the `allowance` view itself does not perform this guard. | Deliberate fail-on-collision design choice, recorded in the project's hashmap design notes. | The key's read and write sides are witnessed by [`06-view-static.json`](scripts/fixtures/weth/06-view-static.json) and [`09-guard-allowance.json`](scripts/fixtures/weth/09-guard-allowance.json); the collision branch itself is untestable by construction (a ~2⁹⁶ search) — see the [fixtures README](scripts/fixtures/weth/README.md#known-limits-of-these-expectations). |
| Ether sent to recognized non-deposit calls *(agreement since 2026-08-09; a divergence before it)* | Only the fallback and `deposit()` are payable ([`WETH9.sol:31-38`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L31-L38)); the other public entry points are nonpayable ([`WETH9.sol:38-75`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L38-L75)) and reject nonzero call value with empty revert data. | The same observable boundary. Every `wethFuncs` entry is wrapped in the shared `nonpayable` combinator (`Blanc/CommonCore.lean`, applied per endpoint in `Blanc/Weth.lean`): after selector dispatch, before the body, `CALLVALUE`/`ISZERO` send a nonzero-value call to `Func.rev` — an empty-data `REVERT(0, 0)`. Only the fallback (`Func.mainWith 1`), which *is* `deposit`, credits `callvalue`; calldata carrying `deposit()`'s own selector is dispatched nowhere, falls through to that payable fallback, and deposits — observably what WETH9's payable `deposit()` does. | **None — agreement**, and recorded here rather than under *Checked similarities* because it was a genuine divergence until 2026-08-09 and this suite carried a success-asserting divergence witness (`11-deviation-value.json`) for its whole prior life. Before that date the dispatcher routed on the selector alone: a recognized call such as `transfer` could succeed while carrying ether, the contract kept the ether, and nobody was credited — a permanently unrecoverable surplus. The wrap moved `wethCode` 888 → 988 bytes (ten guards, ten bytes each) and re-derived the priced walks (`balanceOfGas` 2241 → 2260, warm 241 → 260, `decimalsGas` 139 → 158; every priced walk now carries a zero-call-value hypothesis). | Conformance, user-adjudicated 2026-08-09 under `PORTING.md`'s wager: value-rejection is a feature by prevailing norms — Solidity and Vyper compile nonpayable entry points to exactly this guard, and its modern beneficiary is the buggy integrator, for whom it converts silent permanent loss into a clean revert — and by Blanc's own precedent, the `nonpayable` combinator WETH10 already applied per endpoint, now shared rather than duplicated. Only deposit/fallback calls may carry value. | Witnessed by [`11-agreement-value.json`](scripts/fixtures/weth/11-agreement-value.json): a value-carrying `transfer` is refused while its same-sender, same-cap, zero-value twin is honoured; a value-carrying `balanceOf` probe is refused the two-slot way; `deposit()`-selector calldata plus value is honoured as a fallback deposit; and `totalSupply()` ends exactly equal to the internal balance sum. Shown able to catch the old behavior: rebuilt against the pre-change 888-byte artifact, 11 of the case's 21 expectations fail — both refusals become successes and the totals show the stranded wad. |
| Revert data on a failed guard *(agreement since 2026-08-05; a divergence before it)* | WETH9 encodes no reason anywhere. The pinned source's only failure constructs are three reason-less `require`s — [`WETH9.sol:39`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L39) (`withdraw`'s balance check) and [`:63`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L63)/[`:66`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L66) (`transferFrom`'s balance and allowance checks) — with no `revert`, `assert` or `throw` in the file. The deployed runtime agrees and is the stronger evidence: its 3,124 bytes contain **fourteen `REVERT` opcodes and not one `INVALID`**, and *every* one of the fourteen is preceded by `PUSH1 0x00 DUP1`, i.e. `REVERT(0, 0)` — empty return data, and the frame's unused gas handed back rather than burned. | Identical shape, different encoding. Since 2026-08-05 the shared `Blanc.Func.rev` is `pushB256 0 ::: pushB256 0 ::: .last .rev`, so every rev site in `wethCode` is `PUSH0 PUSH0 REVERT` — also `REVERT(0, 0)`. There were **eleven** such sites then; the 2026-08-09 `nonpayable` wrap (row 4) added one per dispatched entry, so the current literal carries **twenty-one**. (`PUSH0` is Shanghai's; WETH9 predates it and spells the same two zero words `PUSH1 0x00 DUP1`.) | **None — agreement**, and it is recorded here rather than under *Checked similarities* because it was **not** an agreement until 2026-08-05 and this suite ran for months against the divergent behavior. Before that date `Func.rev` was a bare `REVERT` over whatever two words a guard happened to leave live, which `REVERT` reads as `(offset, size)`: a Blanc-WETH guard failure was a garbage-data revert, a stack-underflow halt, or a memory-expansion out-of-gas halt — and the latter two consume the frame's entire gas allowance, which WETH9 never does. That divergence, its three shapes, and the normalization that removed them are catalogued at [`FMINT_DEVIATIONS.md` row 20](FMINT_DEVIATIONS.md); the fix was to the one shared definition in `Blanc/CommonCore.lean`, so it reached both contracts at once (`wethCode` 866 → 888 bytes, `fmintCode` 1217 → 1257, exactly two bytes per rev site). | Deliberate, and unchanged by the normalization: Blanc has **no error-data machinery** — no reasons, selectors or messages on any failure path. Against OpenZeppelin's typed custom errors that is a deviation (`FMINT_DEVIATIONS.md` row 20); against WETH9, which encodes no reason either, it is agreement. | **Not asserted by this suite, deliberately.** A refusal here records the success flag and the executed marker only (see [On refusals](scripts/fixtures/weth/README.md#on-refusals)); no WETH case inspects returndata or remaining gas, and none was added, since the shape is a property of a definition shared with fmint rather than of anything WETH-specific. The discriminating evidence is fmint's: twelve rejected probes asserting flag `0`, `RETURNDATASIZE + 1 = 1` and an in-EVM gas floor, shown able to catch each old shape ([falsifier table](scripts/fixtures/fmint/README.md#what-the-clean-failure-triple-discriminates)). What ties it to WETH is `scripts/check-runtime-bytes.py`, run by `check-weth.sh` and so by CI: every fixture's WETH pre-state code must be byte-identical to the committed 988-byte `wethCode`, the literal whose twenty-one `5f 5f fd` sequences are the normalized sites. |

**Provenance of the deployed-bytecode reading in the fifth row.** The 3,124-byte
runtime was fetched with `eth_getCode` at `0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2`
from two independent public Ethereum nodes on 2026-08-05, which returned
identical bytes (SHA-256 `5566bf50796faf93c9b6f6adacd3b32c70bfe16b48ffc59db6cd144cbdc89739`),
and was then disassembled with a PUSH-aware scan so opcode counts cannot be
confused with push data. That scan is the source of "fourteen `REVERT`, zero
`INVALID`, every one of them `PUSH1 0x00 DUP1 REVERT`". It is a reading of the
deployed artifact, reproducible from the digest above; it is not a claim that
the pinned source compiles to those bytes under any particular `solc`.

## Checked similarities

The comparison also covered calldata truncation and trailing data,
fallback-to-deposit routing, event topics/data, Boolean return values,
`totalSupply`, withdrawal's stipend-limited call, and the maximum-`uint256`
allowance exception. No observable divergence was identified in those items.
This registry is about behavior, not a claim that the implementations share
storage, source, or bytecode.
