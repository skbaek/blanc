# Blanc WETH deviations from deployed WETH9

Blanc's WETH is a proof-oriented reimplementation, not a source or bytecode
model of the WETH9 contract deployed at
[`0xC02a…6Cc2`](https://etherscan.io/address/0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2#code).
This registry catalogues observable semantic differences found by comparing
`Blanc/Weth.lean` with the canonical
[`WETH9.sol`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol).

The first four rows are the four **deviation claims** the fixture suite and
`gen-weth-fixtures.py` refer to by number; they are in a fixed order and new
rows go at the end. The fifth row is not a deviation — it is an **agreement**
that used to be one, kept in the table rather than under *Checked
similarities* because its history is what several of this suite's harness
accommodations were about.

| Behavior | Deployed WETH9 semantics | Blanc semantics | Observable consequence | Project stance | Fixture evidence |
|---|---|---|---|---|---|
| Address words with nonzero upper 96 bits | Solidity's address parameters are 160-bit values. The deployed Solidity 0.4.x decoder ignores dirty higher-order bits, so calls resolve the low 160-bit address ([Solidity compatibility note](https://docs.soliditylang.org/en/v0.7.6/050-breaking-changes.html#semantic-only-changes)). | Mutating paths reject such words (`approve`, `transfer`, and `transferFrom`: [`Weth.lean:158-165`](Blanc/Weth.lean#L158-L165), [`Weth.lean:220-225`](Blanc/Weth.lean#L220-L225), [`Weth.lean:268-279`](Blanc/Weth.lean#L268-L279)). The `balanceOf` and `allowance` views instead use the full calldata words as storage-key material without an address check ([`Weth.lean:108-124`](Blanc/Weth.lean#L108-L124)). | A noncanonical ABI word that WETH9 aliases to its low-160-bit address either reverts in a Blanc mutator or queries a different Blanc storage key. | No equivalence claim; callers should use canonical ABI encoding. | Discharged by [`10-deviation-address.json`](scripts/fixtures/weth/10-deviation-address.json): the mutators refuse the dirty word in every position while honouring the canonical alias, and `balanceOf` answers different values for the two — neither masking nor checking. |
| Balance storage layout | `balanceOf` is a Solidity mapping declared first ([`WETH9.sol:28`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L28)), so balances occupy mapping-derived slots rather than slots equal to addresses. | Deposits and transfers use the raw 256-bit address word itself as the storage slot ([`Weth.lean:21-26`](Blanc/Weth.lean#L21-L26), [`Weth.lean:184-189`](Blanc/Weth.lean#L184-L189)). | Blanc storage proofs and states cannot be interpreted as WETH9's deployed storage image; the same account's balance lives at a different slot. | Deliberately simple proof-oriented representation; no storage-layout compatibility claim. | No case of its own — structural, and witnessed by every case in the [fixture suite](scripts/fixtures/weth/README.md#known-limits-of-these-expectations), each of which asserts storage at exactly the raw-address-word keys. |
| Allowance storage layout and collision handling | `allowance` is a separate nested Solidity mapping ([`WETH9.sol:29`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L29)); Solidity's [mapping layout](https://docs.soliditylang.org/en/latest/internals/layout_in_storage.html#mappings-and-dynamic-arrays) domain-separates it from `balanceOf` through the declared base slots. WETH9 has no fail-on-hash-collision branch. | Blanc stores an allowance at `keccak256(src ‖ dst)`. If that 256-bit hash is also a valid raw-address balance key, `approve` and allowance-consuming `transferFrom` revert instead of writing or reading through the collision ([`Weth.lean:141-167`](Blanc/Weth.lean#L141-L167), [`Weth.lean:245-265`](Blanc/Weth.lean#L245-L265)). | The allowance key is incompatible with WETH9 storage. In the exceptional collision case, an operation WETH9 permits fails in Blanc; the `allowance` view itself does not perform this guard. | Deliberate fail-on-collision design choice, recorded in the project's hashmap design notes. | The key's read and write sides are witnessed by [`06-view-static.json`](scripts/fixtures/weth/06-view-static.json) and [`09-guard-allowance.json`](scripts/fixtures/weth/09-guard-allowance.json); the collision branch itself is untestable by construction (a ~2⁹⁶ search) — see the [fixtures README](scripts/fixtures/weth/README.md#known-limits-of-these-expectations). |
| Ether sent to recognized non-deposit calls | Only the fallback and `deposit()` are payable ([`WETH9.sol:31-38`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L31-L38)); the other public entry points are nonpayable ([`WETH9.sol:38-75`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L38-L75)) and reject nonzero call value. | The selector dispatcher routes directly to every recognized function without checking call value ([`Weth.lean:305-327`](Blanc/Weth.lean#L305-L327)); only the deposit implementation credits `callvalue` ([`Weth.lean:21-26`](Blanc/Weth.lean#L21-L26)). | A recognized Blanc call such as `transfer` can succeed while also sending Ether to the contract, without minting the sender the corresponding WETH balance. WETH9 rejects that call. | No equivalence claim; only deposit/fallback calls should carry value. | Discharged by [`11-deviation-value.json`](scripts/fixtures/weth/11-deviation-value.json): a payable `transfer` succeeds, WETH's ether rises with nobody credited, and a follow-up read shows the surplus is unbacked ether, not an unbacked balance. |
| Revert data on a failed guard *(agreement since 2026-08-05; a divergence before it)* | WETH9 encodes no reason anywhere. The pinned source's only failure constructs are three reason-less `require`s — [`WETH9.sol:39`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L39) (`withdraw`'s balance check) and [`:63`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L63)/[`:66`](https://github.com/gnosis/canonical-weth/blob/0dd1ea3e295eef916d0c6223ec63141137d22d67/contracts/WETH9.sol#L66) (`transferFrom`'s balance and allowance checks) — with no `revert`, `assert` or `throw` in the file. The deployed runtime agrees and is the stronger evidence: its 3,124 bytes contain **fourteen `REVERT` opcodes and not one `INVALID`**, and *every* one of the fourteen is preceded by `PUSH1 0x00 DUP1`, i.e. `REVERT(0, 0)` — empty return data, and the frame's unused gas handed back rather than burned. | Identical shape, different encoding. Since 2026-08-05 the shared `Blanc.Func.rev` is `pushB256 0 ::: pushB256 0 ::: .last .rev`, so all **eleven** rev sites in `wethCode` are `PUSH0 PUSH0 REVERT` — also `REVERT(0, 0)`. (`PUSH0` is Shanghai's; WETH9 predates it and spells the same two zero words `PUSH1 0x00 DUP1`.) | **None — agreement**, and it is recorded here rather than under *Checked similarities* because it was **not** an agreement until 2026-08-05 and this suite ran for months against the divergent behavior. Before that date `Func.rev` was a bare `REVERT` over whatever two words a guard happened to leave live, which `REVERT` reads as `(offset, size)`: a Blanc-WETH guard failure was a garbage-data revert, a stack-underflow halt, or a memory-expansion out-of-gas halt — and the latter two consume the frame's entire gas allowance, which WETH9 never does. That divergence, its three shapes, and the normalization that removed them are catalogued at [`FMINT_DEVIATIONS.md` row 20](FMINT_DEVIATIONS.md); the fix was to the one shared definition in `Blanc/CommonCore.lean`, so it reached both contracts at once (`wethCode` 866 → 888 bytes, `fmintCode` 1217 → 1257, exactly two bytes per rev site). | Deliberate, and unchanged by the normalization: Blanc has **no error-data machinery** — no reasons, selectors or messages on any failure path. Against OpenZeppelin's typed custom errors that is a deviation (`FMINT_DEVIATIONS.md` row 20); against WETH9, which encodes no reason either, it is agreement. | **Not asserted by this suite, deliberately.** A refusal here records the success flag and the executed marker only (see [On refusals](scripts/fixtures/weth/README.md#on-refusals)); no WETH case inspects returndata or remaining gas, and none was added, since the shape is a property of a definition shared with fmint rather than of anything WETH-specific. The discriminating evidence is fmint's: twelve rejected probes asserting flag `0`, `RETURNDATASIZE + 1 = 1` and an in-EVM gas floor, shown able to catch each old shape ([falsifier table](scripts/fixtures/fmint/README.md#what-the-clean-failure-triple-discriminates)). What ties it to WETH is `scripts/check-runtime-bytes.py`, run by `check-weth.sh` and so by CI: every fixture's WETH pre-state code must be byte-identical to the committed 888-byte `wethCode`, which is the literal whose eleven `5f 5f fd` sequences are the normalized sites. |

**Provenance of the deployed-bytecode reading in the fifth row.** The 3,124-byte
runtime was fetched with `eth_getCode` at `0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2`
from two independent public Ethereum nodes on 2026-08-05, which returned
identical bytes (SHA-256 `5566bf50796faf93c9b6f6adacd3b32c70bfe16b48ffc59db6cd144cbdc89739`),
and was then disassembled with a PUSH-aware scan so opcode counts cannot be
confused with push data. That scan is the source of "fourteen `REVERT`, zero
`INVALID`, every one of them `PUSH1 0x00 DUP1 REVERT`". It is a reading of the
deployed artifact, reproducible from the digest above; it is not a claim that
the pinned source compiles to those bytes under any particular `solc`.

Evidence column added by the `weth-evidence` arc; see the [fixture suite's
README](scripts/fixtures/weth/README.md#what-the-suite-establishes) for what
that evidence does and does not establish — specification-checked
differential testing on chosen inputs, not a liveness proof.

## Checked similarities

The comparison also covered calldata truncation and trailing data,
fallback-to-deposit routing, event topics/data, Boolean return values,
`totalSupply`, withdrawal's stipend-limited call, and the maximum-`uint256`
allowance exception. No observable divergence was identified in those items.
This registry is about behavior, not a claim that the implementations share
storage, source, or bytecode.
