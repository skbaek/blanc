# Blanc fmint deviations from OpenZeppelin `ERC20FlashMint`

Blanc's `fmint` is a proof-oriented ERC-20 token with the
[ERC-3156](https://eips.ethereum.org/EIPS/eip-3156) flash-mint extension. It is
**not** a source, storage, or bytecode model of any deployed contract. This
registry catalogues observable semantic differences between `Blanc/Fmint.lean`
and the OpenZeppelin reference below. As with
[`WETH_DEVIATIONS.md`](WETH_DEVIATIONS.md), *the comparison is behavior* — it is
not a claim that the two implementations share storage layout, source, or
bytecode.

## Status of this file

This is the **design-freeze behavior/event matrix**: every behavioral row is
decided *before* the contract is written, so that coding adjudicates nothing.
The `Fixture evidence` column is filled in by the fixture suite (Step 2) and the
OpenZeppelin source walk (Step 3); rows currently read `pending`.

Two defaults recorded in `~/plans/flashmint-proposal.md` as "confirm or veto at
the design-freeze step" are hereby **adopted as written**, since no veto was
issued: the D6 event set (rows 12–14) and the `transferFrom` self-spend bypass
(row 16).

**Claim hygiene.** Nothing in this file is a proof. The conservation invariant
(`totalSupply = Σ balances`) is **unproven pending Arc B** of
`~/plans/flashmint-proposal.md`; the `flashLoan` success specification is Arc C.
No solvency claim is made or implied — during a flash loan the minted supply is
unbacked by construction, which is the point of the mechanism. No liveness claim
is made: fixtures are specification-checked differential testing on chosen
inputs.

| 9 | Callback calldata encoding | Produced by the Solidity ABI encoder: 4-byte selector, five head words (the fifth being the `data` offset `0xa0`), then the `data` length word and the payload, zero-padded to a 32-byte multiple. | Byte-identical layout, built by hand in memory (see the layout table in `Blanc/Fmint.lean`): selector, four value head words, offset word `0xa0`, length word, payload, padded up to a 32-byte multiple. | None — agreement on the encoded bytes. | The layout is fixed in a comment table in the contract source, because it is the one place where a silent off-by-one would produce a decodable-but-wrong callback. | pending (Step 2 — `data` length spectrum 0, 1, 31, 32, 33, multiword) |
| 10 | Callback return-value check | `receiver.onFlashLoan(...) != RETURN_VALUE` reverts.
